## FINDING 1 — a search is silently lost when it is made before hydration

**Where:** `components/search/search-field.tsx:56-64` (the effect), with
`lib/search/history.ts:60` (`rememberSearch`) as the thing that never runs.

### Mechanism

The search form is server-rendered and works with no JavaScript at all — the comment at
`components/search/search-field.tsx:19-21` says so, and that is a deliberate and good
property. The listener that records the query, however, is attached only once React
hydrates:

```ts
useEffect(() => {
  if (!history) return;
  const input = inputRef.current;
  const form = input?.form;
  if (!input || !form) return;
  const onSubmit = () => rememberSearch(input.value);
  form.addEventListener("submit", onSubmit);
  return () => form.removeEventListener("submit", onSubmit);
}, [history]);
```

So there is a window — first paint to hydration — in which the form is fully
submittable but nothing is listening. A submit inside that window navigates away and
`rememberSearch` is never called.

### What the reader sees

Someone who types a query and searches immediately, without waiting, silently loses that
search from «ئىزدەش تارىخى». No error, nothing to report: recent searches simply have
gaps in them. The window is longer on a slow phone, so the readers most likely to hit it
are the ones on the weakest devices — precisely backwards for this library's audience.

### How it was found

It is also the cause of a long-standing flaky test:
`tests/keyboard.spec.ts:151` («recent searches › offers what was searched before, and
only for an empty box»). Playwright clicks faster than a person, so it loses the race
often. Measured on 2026-08-29 at 375×667, on the **pre-domain-move** commit `b7c6ab1`:
**2 of 3 runs failed**; with the domain-move commits applied, 2 of 2 failed. Same error
(`expect(locator).toBeVisible() failed`), same viewport, comparable rate — the flake
predates the domain move and was not worsened by it.

### Suggested fix

Record on the **results page** instead of at submit time. `/search` already receives the
query as `?q=`, so an effect there can call `rememberSearch(q)` after hydration. The race
disappears, because the effect records whenever it happens to run rather than having to
beat a navigation; and it records what was actually searched rather than whatever
happened to be in the box at submit time. The submit listener can then be deleted.

### Also, while in this file

The comment above the effect claims *"Listening in the capture phase means it runs before
the navigation"*, but `form.addEventListener("submit", onSubmit)` passes no
`{ capture: true }`. The behaviour is fine either way — a handler on the form element
itself runs before the navigation — but the comment describes code that is not there.

### Related

Same defect class as the memory note *"a synthetic `selectionchange` fired before
hydration is simply lost"*, and as the flaky
`tests/ai.spec.ts:148` / `tests/ai.spec.ts:261`, which fail with
`locator.check: Clicking the checkbox did not change its state` — a click landing on
`ai-enable` before React attaches its `onChange`. It may be worth one prompt covering all
the pre-hydration races together rather than three separate ones.

## FINDING 2 — the draft-book RLS tests depend on live data, and skip themselves

**Where:** `tests/security.spec.ts:51` and `tests/security.spec.ts:225`, both
`test.skip(!draft, "no draft book in the library to test against")`.

### Mechanism

Both tests first ask the real library for any book with `status = 'draft'`, and skip
themselves when there is none. The library contains no draft today, so on 2026-08-29 both
skipped.

### Why it matters

The assertion those two tests carry — **an unpublished book is not visible to an
anonymous reader**, neither its pages (`:43`) nor its detail page (`:217`) — is therefore
currently never executed. That is a coverage gap on a security property, and it fails
**silently**: the suite reports green, and the skip is one line among hundreds of passes.
A test that quietly stops testing is worse than a test that is missing, because the green
run is taken as evidence.

The property itself is intact — RLS is enforced in the database, and no recent work has
touched policies or migrations — but nothing in CI is proving that any more.

### Suggested fix

Seed the state rather than hope the production library supplies it, using the pattern
this suite already relies on for the published book:

1. Add `SEED_DRAFT_BOOK_TITLE` and `SEED_DRAFT_BOOK_HASH` to `tests/env.ts`, alongside
   the existing `SEED_BOOK_*` constants.
2. In `tests/auth.setup.ts`, seed a book with `status: "draft"` and at least one
   `book_pages` row — `security.spec.ts:43` reads its pages, so a book with no pages
   would pass for the wrong reason. Use the service role, and delete by `file_hash`
   before inserting, exactly as the published seed does at `tests/auth.setup.ts:127`.
3. In `tests/auth.teardown.ts`, add
   `await admin.from("books").delete().eq("file_hash", SEED_DRAFT_BOOK_HASH);`
   beside the two that are already there. Pages cascade with the book row, as that file
   already notes.
4. In `tests/security.spec.ts`, replace both `test.skip(!draft, …)` guards with a read of
   the seeded draft, and **fail** if it is absent. A missing seed is a bug in the setup
   project, not a reason to stop asserting a security property.

**On the constraint that the suite runs against real Supabase and must leave nothing
behind:** this adds no new risk beyond what the published seed already carries, and
slightly less. A draft is invisible to the public by definition — that invisibility is
the very thing under test — so it cannot reach a reader even while it exists. The
delete-before-insert plus the teardown is the same belt-and-braces already proven for
`SEED_BOOK_HASH` and `SEED_MD_BOOK_HASH`; the worst case of an interrupted run is one
marked row sitting in the owner's admin list until the next run removes it.

### While nearby

`tests/security.spec.ts` carries four more data-dependent skips of the same shape —
`:150` (`library too small`), `:158` (`no usable word`), `:242` (`no published book`) and
the file-level `:7` (`Supabase env not configured`). The file-level one is the dangerous
shape: were it ever to fire, all thirteen security tests would vanish from a green run
without a word. It did **not** fire on 2026-08-29 — the security suite really did run —
but it is worth making that loud rather than silent, for example by failing the run
outright when the security suite is asked for and cannot be satisfied.
